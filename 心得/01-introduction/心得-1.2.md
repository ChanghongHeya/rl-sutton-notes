# §1.2 心得：RL 四特征 + 推荐系统是不是 RL

## 我想记住的两条

> 1. RL 问题的四个共同特征：**主动交互 / 目标+不确定 / 延迟后果 / 经验学习**——这是判断"这是不是 RL 问题"的检查清单。
> 2. 训练一个推荐系统、每天根据用户点击日志离线重训——**不是经典 RL，是 SL（监督学习）**。

## 修正与补充

✓ **两条都对，而且抓的点很关键**——四特征是教材在 §1.2 例子之后**亲自归纳**的，可以直接当面试答题模板用。

### ① 把四特征压成口诀（方便背诵）

> **交互 · 目标 · 延迟 · 试错**

- **交互 (active interaction)**：动作改变环境 → 数据分布随策略变（非 i.i.d.）
- **目标 (goal under uncertainty)**：有清晰目标但环境随机/未知 → 必须边学边决策
- **延迟 (delayed consequences)**：当前动作影响未来 → 关心累积奖励而非即时
- **试错 (learning from experience)**：评价式反馈，做了才知道好坏 → 必须探索

**面试答题模板**：被问"RL 和 SL 的区别"时，先答 §1.1 的反馈类型差异（评价式 vs 指令式），再加这四条特征，比单说"RL 没有 label"高一个层次。

### ② 推荐系统这题——再想深一层

教材意义上"是不是 RL"的判别，**关键不是有没有 reward**，而是"**模型动作会不会反过来改变下次拿到的数据分布**"。

| 推荐系统形态 | 范式 | 为什么 |
|---|---|---|
| 离线日志重训（你这题） | **SL** | 日志是固定数据集，今天的模型不影响明天的日志生成（数据分布由旧模型决定，但建模时**当作**给定） |
| Contextual Bandit（如新闻推荐 ε-greedy） | **退化 RL（单步）** | 推哪个会**立刻影响**下次能观察到的反馈（没推过的就没数据）→ 探索-利用回来了 |
| 全 RL 推荐（session 级 / 长期价值） | **完整 RL** | 显式建模"这次推 A 影响用户后续 N 步的状态和点击" |

→ 工业界 90% 的推荐还是 SL，因为反馈循环慢、bandit 探索代价高。但 **YouTube / TikTok 短视频流**已经在做长 horizon RL 了。

### ③ 这条特征清单**直接对应你 LLM-RL 交通控制项目**的痛点

按四特征 check 一下你当前的"单步 GRPO"设定：

| 特征 | 你当前的设定 | 是否真的满足 |
|---|---|---|
| 主动交互 | LLM 输出信号灯方案 → 影响下一秒车流 | ✓ |
| 目标+不确定 | 通行效率最大化，路况随机 | ✓ |
| **延迟后果** | 单步 GRPO 只看当前一步 reward | **✗ 退化掉了** |
| 经验学习 | 从 rollout 学 | ✓ |

→ 这就是为什么你的项目"退化成单步 bandit"——**正是丢掉了第三条"延迟后果"特征**。修复路径（之前讨论过的）：n-step return / TD bootstrap / 把未来 N 分钟预测塞进 r_t。

## 修正后的版本（建议内化）

> **判断"这是不是 RL 问题"的四特征清单**：
> 交互（动作改变数据分布）· 目标（不确定下追目标）· 延迟（动作有长尾后果）· 试错（评价式反馈学习）。
>
> 缺任何一条都会退化：
> - 缺"交互" → SL
> - 缺"延迟" → contextual bandit（单步 RL）
> - 缺"试错" → 规划/控制（model-based）
